* Emacs Configuration — Agent Rules

** Project Rule Precedence

This file contains project-specific conventions and operational details for this Doom Emacs configuration. It supplements the global rules in [[file:../nix.d/AGENTS.org][AGENTS.org]], the target of ~AGENTS.md~. When the two documents conflict on a specific point, this project's README.org takes precedence for work within this repository. It does not replace Emacs or upstream package documentation.

** Documentation Boundary

Follow the global *Rule Placement and Maintenance* section. Unless explicitly directed, add troubleshooting notes to the relevant skill's existing ~references/~ directory; do not create project-level documentation without explicit direction.

** Core Principles

The global *Scope and Design* and *Diagnosis and Verification* sections govern module boundaries, trade-offs, default overrides, and root-cause confirmation. The following rules specify their Emacs application.

- *Flat module layout*: Active ~init-*.el~ modules live directly under ~lisp/~. When a module grows too broad, add focused sibling ~init-*.el~ files instead of nested directories. Name cross-feature integrations ~init-<source>-<target>.el~; avoid generic catch-all modules and package-per-file fragmentation.
- *Do not fragment Doom-owned configuration*: When extending an existing Doom configuration or keymap with a small amount of user configuration, place it in the closest existing functional module. Do not create or retain another ~init-*.el~ solely to wrap the Doom namespace or a compact binding group.
- *Runtime validation before file writes*: For Elisp and other interpreted configuration, proposed behavior must be tested in the live runtime first via ~emacsclient -e~ or another direct temporary eval path. Confirm the behavior works before editing the persistent configuration file.
- *Reload required feature modules explicitly*: ~doom/reload~ resets Doom-managed state but does not re-evaluate ~init-*.el~ files already loaded through ~require~, because their features remain provided. After ~doom/reload~ finishes, explicitly load affected modules and verify their settings, or test in a fresh Emacs process. A successful reload message alone does not verify user module configuration.
- *Reload-safe timer initialization*: Start persistent configuration timers by calling an idempotent scheduler at module load. The scheduler must cancel its existing timer before replacing it; do not register this startup through ~doom-after-modules-config-hook~, which runs before the user configuration in the current Doom lifecycle.
- *Host-aware configuration*: Active hosts are ~nixos-nuc~, ~macos-m1~, and ~ubuntu2204~.
- *Separation of concerns*: Input methods register themselves on editing-state hooks in their own module; the editor module must not depend on input-method packages.
- *Doom module override discipline*: Doom evaluates module configuration, then ~doom-after-modules-config-hook~, then the user configuration. Deferred package configuration can run later. Place overrides after the confirmed writer for that feature and verify both fresh startup and reload; do not assume the global hook runs after user configuration.
- *Runtime assets*: Non-Elisp files required by loaded features belong under ~etc/~, not ~lisp/dev/~. Reserve ~lisp/dev/~ for development/debug Elisp that is not part of normal startup.

** Configuration Rules

*** File Placement

- *Doom modules*: Changes in ~init.el~ (enable/disable modules)
- *Package declarations*: Add ~package!~ forms in ~packages.el~
- *Helper functions*: Keep single-use helpers in the owning ~init-*.el~. Extract a helper library only for substantial logic shared by multiple modules; apply the global *Justify helpers* rule before introducing a helper.
- *Load order*: ~config.el~ requires modules in grouped order (infrastructure → appearance/input → dev tools → org ecosystem → reading → apps). Global predicates/path constants stay at the top of ~config.el~, except predicates needed by ~doom!~, which are defined once in ~init.el~.

*** Code Style

- Use ~;;; filename.el --- description~ header comment; ~(provide 'filename)~ at end.
- *Use ~setup~ for declarative configuration*: Feature options, global hooks, list additions, advice, autoloads, and key bindings belong in ~setup~ forms. Do not use Doom DSL such as ~after!~, ~add-hook!~, ~map!~, ~cmd!~, or ~define-advice~ when the project setup DSL can express the same behavior. Doom module declarations, package declarations, variables, maps, and lifecycle hooks remain valid integration contracts.
- *Keep local setup directives warning-free*: Use the project ~:setopt~ directive for setup-managed options. Do not redefine or call upstream setup directives such as ~:option~ when they emit deprecation warnings.
- *Compose setup primitives before extending the DSL*: Prefer orthogonal combinations of existing directives such as ~:with-feature~, ~:with-map~, ~:bind~, and ~:hooks~. Do not add convenience directives that only preselect a map, prefix, feature, or common argument pattern; add a setup extension only when it provides distinct semantics that cannot be expressed clearly by composition and has demonstrated reuse.
- *Keep runtime implementation native*: State transitions, buffer-local lifecycle hooks, mode keymap construction, timers, and temporary mutation inside functions or mode bodies should remain ordinary Elisp rather than being forced into setup directives.
- *Centralize Meow mode-state policy*: Keep all ~meow-mode-state-list~ mappings in the ~setup meow~ block in ~init-editor.el~, grouped by the associated feature with ~:with-feature~. Feature modules must not mutate this global policy list.
- *Keep ~setup :when-loaded~ narrow*: Put plain ~:setopt~, hooks, autoloads, and top-level ~:also-load~ outside ~:when-loaded~ unless timing must follow a confirmed upstream writer or loaded definitions. Never nest ~:also-load~ inside ~:when-loaded~.
- Prefer ~setopt~ over ~setq~ for user options.
- *Separate feature ownership from load timing*: Inside a ~setup~ block, group options owned by another loadable feature under ~:with-feature~, and use ~:bind-into~ for another feature's keymap. ~:with-feature~ changes setup context but does not defer ~:setopt~; preserve timing when regrouping. Use ~:when-loaded~ only when code needs loaded definitions or must run after a confirmed upstream writer.
- *Guard ~pcase~-derived paths*: When a variable is set via ~(pcase system-name ...)~ and not all hosts are covered, wrap it with ~(when var ...)~ before inserting into lists.
- *Named hook and advice targets*: Keep package connection points in ~init-*.el~, but make targets named functions when they need stable removal or debugging. Do not introduce named functions solely for static option assignments; use an anonymous ~:hooks~ callback. Give anonymous reload-sensitive advice a stable identity with ~:advice~ and ~(:named NAME FUNCTION)~.
- *Use setup list and key primitives*: Replace declarative ~add-to-list~ calls with ~:setopt~ plus ~prepend~/~prepend*~, preserving order. Express Doom leader maps with ~:with-map~ and localleader prefixes with ~:bind~ key expressions so key descriptions remain intact without ~map!~.
- *Fonts are required local dependencies*: Font configuration should name required installed fonts directly and fail loudly when absent. Validate availability only in a graphical frame, where ~find-font~ has a font backend; a daemon or terminal frame returning nil is not evidence that a font is missing. No fallback chains or warning-only missing-font behavior.
- *macOS frame policy*: Every graphical frame must open in native space-based fullscreen with frame tabbing disabled. Configure this declaratively through frame defaults; never use delayed fullscreen toggle hooks.
- *Do not define config functions from personal Org Babel blocks at startup*: Functions used by Emacs configuration must live in ~lisp/~.
- *Calibre rules*: Preserve field-scoped overrides, annotated copies, and independent progress tracking.

*** Package Management

- Keep package recipes portable and declarative. Use ~DOOMGITCONFIG~ with cross-platform credential helpers; do not encode credentials or macOS-only keychain helpers in synchronized recipes.

** External Dependencies

External tools are managed through [[file:../nix.d/modules/emacs.nix][the Nix Emacs module]], not ad hoc installation commands.

** Definition of Done

Apply the global *Delivery* criteria. For configuration changes, also verify:

- ~doom sync~ completed without errors
- Emacs restarts successfully
- Feature works as expected
- No errors in ~*Messages*~ buffer
- External dependencies (if any) added to Nix and applied
- Before committing configuration changes: verify ~emacsclient -e '(doom/reload)'~ reports success, explicitly reload affected feature modules as required above, and check ~*Messages*~ for new errors. For structural changes, search ~config.el~ and ~lisp/~ for dangling ~require~ calls.

For rule-document-only changes, check constraint preservation, references, Org formatting, and ~git diff --check~; ~doom sync~, runtime evaluation, and Emacs restart/reload are not required.
